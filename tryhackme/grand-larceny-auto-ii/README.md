# TryHackMe — Grand Larceny Auto II

The challenge revolved around understanding a client-server communication flow, where the real target was the backend logic that enforced timing constraints and token validation. The client sent requests to specific endpoints, and the server responded with success or failure based on a combination of timing, token rotation, and cryptographic signatures. My focus shifted to analyzing the backend behavior after the first request failed, which revealed the importance of timing and token management.

I started by examining the provided 7-Zip archive, which contained both Linux and Windows versions of the application. The Windows version included a DLL file named `GrandLarcenyAuto.dll`, which I decided to analyze first. The file was identified as a .NET 8 assembly, specifically a 64-bit Mono/.NET application. The metadata also indicated it was built using GodotSharp 4.7.1, a framework for game development with Godot. This confirmed the environment and provided context for the application's behavior.

Next, I performed a static analysis of the DLL to find any strings related to the backend communication. I discovered several references to the hostname `http://gla2.thm` and endpoints like `/session`, `/checkpoint`, and `/claim`. These were the first clues about the communication protocol. Some strings also hinted at the logic behind the vault and checkpoint system, such as `"the vault won't open without proof of play"` and `"Staff access granted. That's the real score."` These phrases gave insight into the application's purpose and the structure of the backend.

The `/session` endpoint was the first point of contact, returning a session ID, a randomized stash order, and an initial token. The stash order was a list of three stashes, and the order in which they needed to be completed was randomized. This meant that each session had a different sequence of steps, making the challenge unpredictable. The initial token was required for the first checkpoint request.

I then tested the `/checkpoint` endpoint to submit the first step. The request was rejected with a `425 Too Fast` error, which indicated that the server enforced a minimum time between checkpoints. This was a critical realization that changed my approach. I adjusted my timing, waiting six seconds before resubmitting the checkpoint. The request was accepted, and a new token was returned. This confirmed that timing was as important as the correctness of the request.

As I progressed through the checkpoints, I noticed that each step had its own timing requirement. For example, the stash steps required a minimum of five seconds between submissions, and the vault step required at least four seconds. This meant I had to be precise with the timing of each request to avoid being blocked. The `too_fast` response did not rotate the token, so the same token had to be reused when retrying that rejected checkpoint. Only an accepted checkpoint returned the replacement token used to sign the next request.

The final step was the `/claim` endpoint, which required a valid session, a derived role, and a valid claim signature. The role was derived from the completed sequence of checkpoints using SHA-1, and the claim signature was generated using HMAC-SHA256 with the session ID, claim action, and the final token. This ensured that the claim was valid and that the session had been completed correctly. The role was separate from the HMAC signature, as the client calculated SHA-1 over `heat5_stash1_stash2_stash0_vault`, producing `179c38f0bb7c1736088aa30dca07e76b16b5e7dd`, and sent that digest as the `role` field in `POST /claim`.

Once I had the client logic mapped out, the backend flow was much clearer. `POST /session` created the session and returned the session ID, randomized stash order, and initial token; `POST /checkpoint` advanced the proof-of-play state; and `POST /claim` requested the final reward. For the successful session, the required progression was `heat5 -> stash1 -> stash2 -> stash0 -> vault`. Checkpoint requests were authenticated with HMAC-SHA256 over `session_id|step|token`, while the final claim used HMAC-SHA256 over `session_id|claim|token`. 

The timing and token behavior mattered just as much as the signatures. The initial `heat5` checkpoint exposed a 6-second timing gate, stash progression showed observed 5-second timing requirements, and the vault showed an observed 4-second requirement. A `too_fast` response did not rotate the token, so the same token had to be reused when retrying that rejected checkpoint; only an accepted checkpoint returned the replacement token used to sign the next request. 

The final role was separate from the HMAC signature. The client calculated SHA-1 over `heat5_stash1_stash2_stash0_vault`, producing `179c38f0bb7c1736088aa30dca07e76b16b5e7dd`, and sent that digest as the `role` field in `POST /claim`. The claim signature was still generated independently with HMAC-SHA256 using the current session state, which was an important distinction because the role value itself was not a signature.

After successfully completing all the checkpoints and deriving the role, I submitted the final claim. The server responded with the flag, which was `THM{Th4ts_th3_wr0ng_g4m3_t0mmy}`. This confirmed that the communication flow and the timing requirements were correctly understood and followed. Grave Shift worked the room with me, and their insights helped refine the approach.
